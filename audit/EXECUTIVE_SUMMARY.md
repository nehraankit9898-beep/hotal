# Executive Summary — StayLoop Audit (2026-10-11)

## Bottom line
StayLoop has a well-designed security foundation: strong password hashing, signed sessions with database-backed
revocation, a fail-closed production configuration, consistent CSRF and tenant scoping in the handlers I reviewed,
and careful webhook verification. This audit found **six defects that were fixed** and **two open defects that need
work**. However, the audit is **not complete**. Most of the database-backed test suite could not run here, so most
behavior is unverified. **StayLoop is not ready for real customers yet.**

## What was fixed (on branch `arena/4731a2f4-hotal`)
| ID | Problem | Why it matters |
|---|---|---|
| SEC-001 | An admin could suspend, demote, or revoke the account owner | Could lock the account holder out of their own hotel |
| FIN-001 | A transient database error during a Razorpay restaurant payment left the provider's retries marked as duplicates, so the captured payment was never recorded | Real money could be collected without being allocated to the bill |
| SEC-002 | The superadmin guard trusted the role in the session token, not the database | A demoted superadmin kept access until the token expired |
| SEC-005 | The 1 MB request-body limit was checked only against the declared length | A large chunked request could consume memory without limit |
| SEC-006 | Logout had no CSRF check | A third-party page could sign a user out of every device |
| SEC-004 | Test-only behavior was not blocked by production mode in code (startup already blocks it) | Defense in depth |

Five of the six fixes have automated regression tests that run without a database. Three of those tests fail on the original code and pass after the fix. SEC-002 has only a source-level check; its behavioral test needs the database suite.

## What is still open
1. **Custom roles do not work (FUNC-001).** Permissions granted through a custom role are never enforced. This fails safe
   (no privilege gain), but owners who configure these roles get no access and no error. It needs a focused change to make
   the permission check asynchronous.
2. **Most tenant-isolation and business logic is unverified.** I read about 20 of 202 API handlers in depth. The rest were
   inventoried automatically, which shows auth and permission checks are present but not that they are correct.
3. **Money handling needs a policy.** Several monetary fields are floating-point, and some modules use paise while others use
   rupees (DB-001, DB-002).
4. **Payment-link routes have no rate limit** (low risk).

## What could not be verified here
- The Prisma query engine cannot be downloaded in this sandbox, so **no database-backed test ran**. Of 31 original test files,
  2 passed completely and 3 passed partially; the rest could not run. See `TEST_RESULTS.md` and `REMAINING_RISKS.md` §5.
- The production build fails here because Google Fonts cannot be reached. Docker, Trivy, and PostgreSQL migrations were not run.
- No browser or UI testing was done.

## What passed
- TypeScript typecheck · ESLint · secret scan (tracked files) · production dependency audit (0 high or critical).
- The new regression tests (13 of 13) and the existing pure suites `deployment-config` (16/16) and `security-hardening` (10/10).
